The big picture

MoveInSync asked two things: why is our Play Store rating lower than it should be, and what should we do about it. They also said they would keep asking. So the project is a pipeline, not a one-off analysis. A pipeline is a chain of small programs where each one reads files, does one job, and writes files for the next.

Six stages run in order. One command, python run.py, runs them all.

The pipeline. Blue stages gather data, orange stages interpret it, green stages turn it into something to read. Under each stage is the file it writes.

Three ideas explain most of the design:

  • Each stage only talks to the next through files. You can run any stage alone, open its output, and see exactly what it did.
  • Every number is computed once, in one place. Stage 5 writes metrics.json, and every output reads from it: the report, the digest, the backlog and the manual-review list. A figure cannot be different in two places.
  • The parts that need judgement are written down as files, not buried in code. The themes, the labelling rules and the recommendations are plain text you can read and change.

The six stages

Stage 1: Pull

Job: fetch public reviews and ratings and save them. Code: ratings/pull.py for Play, ratings/ios.py for the App Store.

Google has no public API for reading another company's reviews, so this stage uses an open-source library, google-play-scraper, that reads the same data the Play Store web page shows.

What it saves

  • Reviews, one row each, in data/reviews_<app>.csv: the star score, the date, the text, the app version, and any reply from the developer. Reviewer names are never saved.
  • A snapshot of what the Play page says right now, added to data/snapshots.jsonl: the rating and how many ratings fall on each star.
  • The rating in each country, added to data/country_snapshots.jsonl. Play shows a different rating depending on which country you view it from.
  • iOS reviews in data/ios_reviews.csv. Apple's public feed only gives the latest 500 or so.

First run and later runs

The first run is a backfill: it pages back through every review ever written, which takes several minutes. Every later run is incremental: it re-reads only the last 14 days, picks up anything new or edited, and finishes in under a minute.

Details that matter

  • It does not trust an empty answer. The library returns nothing both when there are no more reviews and when Google blocks the request. So an empty page is retried, and a sweep that stops early is logged as incomplete in data/pull_log.txt.
  • Times are stored in UTC. The library returns times in the computer's own timezone. Without converting, the same review would get a different time on a laptop in India and on GitHub's servers.
  • Identifying details are removed. Vehicle numbers, phone numbers and email addresses typed into a review are replaced with a placeholder before saving.
  • If Play cannot be reached, the run continues on the reviews already saved.

Stage 2: Clean

Job: make sure the data can be trusted before anything is computed from it. Code: ratings/clean.py.

It checks for duplicate reviews, scores outside 1 to 5, and dates in the future. It also compares how many reviews were pulled with how many Play itself says exist, and prints that as a coverage percentage. If a check fails, the run stops there with a message, because a report built on bad data is worse than no report.

This file also holds the one function every later stage uses to load reviews, so all stages work from the same checked rows.

Stage 3: Label

Job: decide what each low-star review is complaining about. Code: ratings/classify.py, with the rules in ratings/prompt.md and the themes in ratings/taxonomy.yaml.

This is the one stage a plain script cannot do alone, because it needs reading comprehension. Reviews are short, often mix Hindi and English, and say the same thing in a hundred ways. A language model does the reading. Everything around it is ordinary code that keeps the model honest.

What gets labelled

Reviews of the employee app, on Play and iOS, rated three stars or fewer, written in the last 12 months. Each one gets five things:

FieldMeaningExample
ThemeThe main complaint, chosen from the written listlogin_otp
Second themeA clearly separate second complaint, if there is onesession_logout
OwnerWho would have to act: the app team, operations, an employer's policy, or unclearapp
SafetyDoes the reviewer describe a risk to a personyes / no
After updateDoes the reviewer blame an update or a new versionyes / no

A batch is rejected whole if any review is missing, appears twice, or uses a theme that is not on the list. Nothing half-labelled is ever saved. Once a review has a label it is never sent to the labeller again, so a weekly run only labels that week's new reviews.

The labeller writes one short line per review. 17|login_otp is a complete line: review 17, theme login OTP, everything else at its default. A full line looks like 18|no_show|driver_behaviour|ops|1|0.

Who the labeller is

Two labellers can fill the same cache, and both follow the same two files:

  • Claude Code, through the play-ratings skill. Every label in this repository was made this way.
  • The Claude API, through ratings/llm.py, for runs with nobody present. It switches on when an ANTHROPIC_API_KEY is set. It is tested with a stand-in for the API and has not been run against the live service in this project.

With neither available, the run does not fail. It counts the unlabelled reviews, says so, and builds everything else.

Stage 4: Validate

Job: measure how far the labels can be trusted. Code: ratings/gold.py and ratings/validate.py.

gold.py picks a fixed random sample of 120 labelled reviews and builds a small labelling page, tools/label_gold.html. Those 120 are labelled a second time by someone who has not seen the first labels, and saved as data/gold.csv. This second set is called the check set. validate.py then compares the two and reports:

  • how often they chose the same theme, the same owner, and the same flags;
  • Cohen's kappa, which is agreement after removing what two labellers would agree on by pure chance (0 is chance, 1 is perfect);
  • for each theme, precision (when the first pass said this theme, how often the check set agreed) and recall (of the reviews the check set gave this theme, how many the first pass found);
  • every disagreement, written to data/gold_disagreements.csv so each can be read.
In this project the check set was labelled by a second, separate Claude session and then reviewed by the author. That is weaker than a person labelling from scratch, and the report says so. check_set in config.yaml records who labelled it, and the report words itself from that setting.

Stage 5: Metrics

Job: compute every number once. Code: ratings/metrics.py. Output: docs/data/metrics.json.

It reads the reviews, the snapshots and the labels, and writes one file holding everything the outputs need: the rating by country, the trend by month, each theme's share, reply rates, the reply and safety queues, the evidence for each recommendation, and the validation result. How the trickier numbers are worked out is explained below.

Stage 6: Build

Job: turn metrics.json into things people read. Code: ratings/build.py, with charts drawn by ratings/charts.py and the page layout in ratings/templates/report.html.

  • The report, docs/index.html. A single self-contained page; charts are drawn as SVG by Python, so there is no chart library and no server.
  • The digest, docs/digest.md. A short page that answers the recurring question and lists anything needing attention.
  • The backlog, docs/backlog.csv. One row per recommendation, ready to import into a ticket tracker.
  • The manual-review list, docs/manual_review.csv. Reviews that fitted no theme and are waiting for a person to look at them.

The recommendations show how words and numbers are kept apart. recommendations.yaml holds each ticket's wording and names the themes and phrases that are its evidence. It never states a count. The build fills the counts in from metrics.json, so a ticket's evidence updates itself every week.

How themes work, including new ones

The list of themes was not invented in advance. It was drafted after reading about 650 real low-star reviews, and it lives in ratings/taxonomy.yaml, where each theme has a definition, real examples, a stage of the employee's journey, and a default owner.

A fixed list is what makes this month comparable with last month. But a fixed list would be a trap if a new kind of complaint had nowhere to go. So a complaint that fits nothing is never forced into the nearest theme.

How a new kind of complaint becomes a theme without anyone adding it. Each batch shows the labeller the notes already in use, so the same complaint gets the same wording and can be counted.

Two guards keep this from turning into noise. The threshold of five means one unusual review is not a category. Reusing notes means “driver call fails” and “calls not connecting” do not become two themes.

A person can later promote an automatic theme into a written one, with a proper definition, by adding it to the taxonomy file and running python -m ratings.classify requeue --theme other, which sends those reviews back to be labelled again.

There is also a second alarm. If complaints that fit no theme pass 3% of recent low-star reviews, the digest says the list is going out of date. Both thresholds are in config.yaml.

Marked for manual review

Every review labelled “other” is also marked for manual review. The report lists each one, with its text and note, under “Marked for manual review”, and the same list is written to docs/manual_review.csv so someone can work through it in a spreadsheet. The digest gives the count.

The person reviewing makes one decision per review and records it with one command:

python -m ratings.classify resolve --id 1a2b3c4d --theme trip_details   # it belongs to an existing theme
python -m ratings.classify resolve --id 1a2b3c4d                        # a one-off; keep it as "other"

The id is the short one shown beside each review in the report. The decision is saved in the label cache, marked as made by a person, and the review leaves the list on the next run. If it is a genuinely new problem, add a theme to the taxonomy file first and resolve the review to that.

What this cannot catch: a new problem that looks like an old theme. A new kind of crash is labelled “app won't open”, not a new theme. It shows up instead as that theme growing, which has its own alert.

How the trickier numbers are worked out

Ratings and reviews are different things

A rating is a star score. A review is a rating that came with written text. Most people who rate write nothing, and the ones who do write are far more often unhappy. The store's rating is made of all ratings. So the pipeline uses reviews only to explain why low ratings happen, and takes the size of the problem from the ratings.

The estimated effect of fixing a theme

Each theme has an estimate of how much the rating would rise if that problem went away.

effect = theme's share of low-star reviews
         x  share of all ratings that are 1 or 2 stars
         x  (4  -  the average of those low ratings)

Worked through for login OTP on the Indian listing: it is 7.3% of low-star reviews; 7.1% of all ratings are one or two-star; their average is 1.1. So 0.073 × 0.071 × (4 − 1.1) = about +0.015.

Three assumptions sit inside that, and the report states them: people who rate low without writing have the same complaints as those who write; a satisfied person would have given four stars; and the figure is where the average settles in the long run, not how quickly.

Is a release worse, or just unlucky?

A version with 38 reviews where 37% are low-star looks bad next to the usual 27%. But with only 38 reviews, that could easily be chance. The pipeline works out a 95% confidence interval for each version's low-star share (the Wilson interval) and flags a version only if even the bottom of that range is above the usual share. Over the last year, none is.

The rating of new ratings

Every run saves how many ratings sit on each star. Subtract last week's counts from this week's and you have the stars of ratings added in between, including the silent ones with no text. This series only builds up over time, so it starts from the first run.

When the digest raises a flag

FlagRule
Low-star share is upThe last 30 days are more than 5 points above the last 12 months
A theme is growingIt is at least 5% of recent low-star reviews and at least double its earlier share
A release looks badThe newest version is clearly above the usual share, by the test above
Safety reviews unansweredAny safety-flagged Play review has no developer reply
Reviews waiting for labelsAny in-scope review has no theme yet

Themes going staleUnthemed complaints pass 3% of recent low-star reviews

All these thresholds are in the alerts section of config.yaml.

Run it yourself, end to end

Work through these in order. Each step says what to type, what you should see, and what it proves. Commands are run in a terminal opened in the project folder. You need Python 3.10 or later.

Nothing here can damage the project. The data and outputs are saved in git, so git checkout -- config.yaml data docs puts them back exactly as they were at any point.

2

Run the tests

python -m pytest

You should see a row of dots ending in a line like 25 passed. This proves the label parser, the data checks, the rating arithmetic, redaction and timezone handling all behave as intended.

3

Check the connection to Google Play

python -m ratings.pull --test

You should see one line per app with its name, rating and number of ratings, then fetched 50 reviews and five sample reviews. Nothing is saved. This proves Play is reachable from your machine and the app ids are right.

If it says 0 reviews returned, Google is blocking or rate-limiting you. Wait a few minutes and try again. The rest of this walkthrough still works with --no-pull.

4

Run the whole pipeline

python run.py

It takes about a minute. You should see five headed sections:

SectionWhat to look for
== 1. Pull ==For each app, incremental: re-reading from a date about two weeks back, then N new, T total. A by country line lists seven ratings.
== 2. Clean ==A coverage line per app, then clean: OK.
== 3. Label ==in scope / labelled / pending. If pending is above zero, it tells you how many reviews are waiting.
== 4. Metrics ==The rating, the iOS rating, and the top themes with their shares.
== 5. Build ==wrote four files (the report, digest, backlog and manual-review list), then any ALERT lines.

This proves all six stages run together from one command.

Proving the outputs really are generated

A normal run overwrites the report, digest, backlog, manual-review list and metrics file every time, but overwriting is hard to see. To make it visible, start from nothing:

python run.py --fresh

You should see an extra first section, == 0. Fresh start ==, listing the five files it deleted. For a moment docs/index.html does not exist; by the end of the run all five are back, and the time in the report's footer is the time you ran it.

It only deletes outputs. The pulled reviews and the labels in data/ are kept, because re-downloading eleven years of reviews takes about ten minutes and the labels cannot be recreated by a script.

7

Run one stage alone

Every stage runs by itself, which is how you find where a problem is:

python -m ratings.pull              # fetch new Play reviews and rating snapshots
python -m ratings.ios               # fetch the iOS rating and recent iOS reviews
python -m ratings.clean             # data checks and coverage
python -m ratings.classify status   # how many reviews are labelled or waiting

After validate, open data/gold_disagreements.csv to read the reviews where the two label sets differ.

8

See the labelling loop in action

New low-star reviews only appear a few at a time, so to watch labelling happen, send a small theme back to be labelled again:

python -m ratings.classify requeue --theme boarding
python run.py --no-pull

You should see in the Label section that about a dozen reviews are now awaiting theme labels, and the same message in the digest under “Needs attention”. The rest of the report still builds.

Now open the project in Claude Code and ask: How are our Play Store ratings? The skill exports the waiting reviews, labels them, imports them, rebuilds, and answers. Run python -m ratings.classify status afterwards and pending is back to zero.

The same thing by hand, without Claude Code

The skill only runs three commands and writes one file, so you can do it yourself. After the requeue:

python -m ratings.classify export

Open data/pending/batch_001.txt. Each line is a number, a star rating and a review. Create data/pending/batch_001.labels.txt next to it with one line per review, such as 1|boarding, using theme names from ratings/taxonomy.yaml. Then:

python -m ratings.classify import --by me

Try it once with a made-up theme, or with one review left out. You should see Rejected: followed by the file and the reason, and nothing is saved. Correct the file and import again.

To undo the experiment and return to the committed labels:

git checkout -- data docs
9

Record a manual-review decision

In the report, find “Marked for manual review”. Each review there has a short id. Pick one and decide where it belongs, then record the decision:

python -m ratings.classify resolve --id 028ff030 --theme trip_details
python run.py --no-pull

Use the id you picked in place of 028ff030. Leave out --theme to keep the review as “other” and only mark it as looked at.

You should see a line confirming what was recorded, and after the rebuild the list in the report and the count in the digest are one shorter. This proves a person's judgement can be fed back in without touching any file by hand.

To undo it: git checkout -- data docs

10

Change a setting and watch the result change

Behaviour is controlled from config.yaml, not from the code. Open it and, under alerts, change new_theme_min_reviews from 5 to 6. Then:

python run.py --no-pull

You should see the “New theme created automatically” flag disappear from the run's output. In the report, “Driver call fails (new)” is gone from the themes chart, because five reviews sharing a note is no longer enough; those reviews are counted under “Other” again. Put it back: git checkout -- config.yaml data docs

11

Open the check-set page

Open tools/label_gold.html in a browser. This is the page used to label the 120-review check set. Click a theme, hover over others to read their definitions, tick a flag, press the right arrow. Your work is saved in the browser as you go.

Export CSV downloads a file called gold.csv. Only move it into data/ if you mean to replace the existing check set; otherwise delete the download.

The page itself is built by a script, so it always matches the current themes and rules:

python -m ratings.validate    # compare the labels with data/gold.csv

This proves the reliability check is something a person can redo, not a number to take on trust.

Design decisions, and the reasons

DecisionWhy
A pipeline of small stages, not one scriptEach stage can be run, read and tested alone. When a number looks wrong, you can find which stage produced it.
All numbers in one fileThe report, digest, backlog and manual-review list cannot disagree with each other.
Themes and rules in text filesSomeone who is not a programmer can read exactly how reviews are categorised, and change it.
A language model labels; code checksReading short, mixed-language reviews needs a model. Strict importing means a model's mistake in format can never reach the data.
Each review labelled once and cachedWeekly runs are fast and cheap, and old labels do not shift under you.
No confidence score on labelsA model's own confidence is not reliable. Agreement with a second labelling is a real measurement.
Complaints that fit no theme are listed for a personThe model should not have the last word on something it could not place. A person decides, and the decision is recorded.
New themes appear automatically at five reviewsA new problem should not wait for someone to notice it, but one odd review should not become a category.
The run never stops for a missing network or keyA recurring report that fails whenever Google is slow is not a recurring report.
Times in UTC, fixed line endingsThe same data must come out whether it runs on a laptop or on GitHub. The first weekly run exposed both problems.
Identifying details removed, names never storedThe reviews are public, but this project republishes them.
The report states its own limitsA reader can only act on findings they know how far to trust.

Words used

WordMeaning here
RatingA star score from one to five. Most have no text.
ReviewA rating that came with written text.
Low-starOne or two stars.
ListingThe app's page in one country's Play Store. Each country shows its own rating.
ThemeWhat a review is complaining about, such as “login OTP never arrives”.
OwnerWho would have to act to fix a complaint: the app team, operations, or an employer's policy.
BackfillThe first pull, which fetches the whole history.
IncrementalA later pull, which fetches only what is new.
SnapshotA saved copy of what the store page said at one moment.
CacheSaved results that are reused instead of being worked out again. Here, the labels.
Manual reviewA person looking at a review that fitted no theme and recording where it belongs.
Check setA sample labelled a second time, used to measure how reliable the labels are.
SkillA set of written instructions Claude Code follows for a particular task.
GitHub ActionA job GitHub runs on its own servers, on a schedule or on demand.
GitHub PagesGitHub's free hosting, which serves the docs folder as a website.
